## Receipt contract proposed for joint review

The isolated composition explicitly installs a PAS Ed25519 signing key. Travel pins the public key, PAS origin and destination with the existing owner, target and client registration. The isolated PAS create route calls the existing idempotent conversation-create service after verifying the enrolled human and client. Travel reserves the exact original UUID and title before sending. PAS signs the result of that create transaction, including the returned conversation UUID. Ordinary consumer v1 retains its existing endpoint and behavior.

The create and preview attestations contain the direction-specific receipt schema version, operation, target, client namespace, application, null workspace, PAS owner, verified issuer and subject, conversation UUID, SHA-256 of the exact request bytes, SHA-256 of the exact response bytes, and the actual prepared domain source revision for preview. PAS signs compact, sorted-key UTF-8 JSON and returns the signature in `X-Application-Plan-Receipt`. Travel reconstructs the statement from its stored reservation and current binding. It verifies the raw response, exact frozen model and recipients, three inventory entries, confirmation, and expiry before persisting content-free evidence.

Travel migration 0022 keeps previous bindings without authenticated create provenance unavailable. Its rollback refuses while private bindings or anchors are retained. Travel reserves a preview once and retains ambiguity under the original key. GET-only inspection checks the current private anchor, owner, trip ACL, revision and original key on both sides of the HTTP request. Missing evidence quarantines the result. `not_found` remains an observation for that request and cannot establish that a dispatch did not occur. This preview-only caller exposes no completion or conversation detail through its recovery path.

## Dispatch contract still proposed

- The verified Travel user would authorize a single exact confirmation by agreeing to the frozen inventory and destination. The Travel caller would revalidate the current user, private anchor, trip ACL and revision, then durably record the original continuation UUID and digest of the exact confirmed body before the first POST. A repeated confirmation would join an existing intent or reconcile by GET. The content-free journal is suited to GET-only recovery.
- PAS would own the release decision. Its application-plan authority would have to recheck the authenticated owner/client/target, conversation and branch, canonical Travel projection and PAS memory, and the exact source, runtime and model grants. The prepared payload, caller, runtime installation, connection revision, provider/model and recipient would have to match. Timeout, stale data, revocation or lost continuity would deny release.
- The paired runtime would independently recheck those authorities immediately before the physical send and commit one non-reusable send-start claim scoped to owner/client/target/conversation/original key and payload digest. The claim would need storage independent of PAS receipts and Travel SQL, with explicit restore continuity. PAS and Travel would disable POST retries throughout. PAS would revalidate current permissions on each delta, terminal, status, detail and replay before disclosing output.
- Recovery would use authorized original-key status and matching detail after validated terminal or reconciliation. Unknown, lost continuity and status/detail mismatches would remain unresolved. The paired witness still needs one positive receiving fake POST, zero pre-send denials, at most one across recovery, both contention orderings, each interruption point, independent writer processes and a paired old snapshot restore.
- Native Travel SQL and PAS memory/source changes remain independent of the existing fixture POSIX lock. A revocation can happen between the last read and the remote POST. This is a live E3 blocker even if the coordinated synthetic cases later pass.

## PAS source identity disposition

Scope narrowing places the response signing in the already-divergent private API module and carries the revision through the existing application-plan preview service. It adds no path to either locked runtime scope. Fully removing the earlier shared-runtime changes would drop the paired source authority, canonical projection provenance, or required assembler path. The reviewed planning, offline-benchmark and adaptive contracts therefore remain release gates.

The additive planning v40 and offline benchmark generation 14 proposals are review inputs. Planning owners must supply a freeze date and source-change summary, offline benchmark owners must preregister the successor, and adaptive owners must disposition the inherited changed chat-service bytes and decide how to establish the current conformance seal. Each approved successor needs its own evaluation. Frozen manifests and historical results stay byte-identical. [Baseline and drift evidence](2026-11-22-travel-g1-native-readiness.md)
