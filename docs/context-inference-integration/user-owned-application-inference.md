# User-owned application inference

The private fixture enables a foreground ChatGPT plan turn for an enrolled application. It uses the consumer SDK's create, preview, continue and original-key status methods. The fixture selects a separate request shape with `choice.mode = "user_owned_plan"`. It expects no confirmation for preview and an exact preview confirmation for continuation. Both requests arrive through the normal identity and application-client checks. The published consumer 1.2 contract retains automatic execution. The ordinary API and the standalone bridge cannot mount this fixture.

## Authorization sequence

1. PAS resolves the verified human, exact external client, owner, application and workspace. The app's source separately verifies membership and the record revision. The request requires distinct grants for the PAS source read, the paired local runtime and the onward provider registration. An approved app projection never grants access to memory.
2. The canonical PAS reader checks one explicitly shared memory and its original source turn. Its origin can be another application where the same owner still has access. The separate runtime and provider grants each bind the exact memory, origin, destination and epoch. Installation or sign-in grants neither source nor memory access.
3. The existing assembler prepares the bounded input once. Preview returns destination, model, purpose, context categories and projected fields, the number of complete prior conversation turns selected, an estimate and an expiring confirmation. The history count comes from the same frozen assembly that supplies the prepared package; it contains no message text or identifiers. The exact context remains in a bounded transient PAS preview cache. Confirmation binds the active branch, original key, selected source revisions and timestamps, grant epochs, exact prepared package and provider serialization, recipient, caller, runtime, account-registration binding and intent.
4. PAS writes one routing-root fence and records it with an independent recovery witness. It then issues a short-lived signed v2 dispatch envelope. The paired runtime authenticates the caller and registration and checks the exact account catalog and included-only eligibility before PAS releases the plaintext. PAS rechecks current authority at release. The local runtime revalidates the envelope, account, catalog and payload, then requires current PAS authority under its durable send-start lock.
5. The runtime forwards one request through the bounded Responses serializer. The continuation accepts success from the exact runtime stream and matching durable receipt. PAS rechecks source and identity rights for deltas, completion, stored detail and replay. Original-key status can report an unknown outcome without response text. An unknown send retains both available fences and offers no resend or fallback.

The fixture admits one external projection and one original memory. It can include ordinary complete history from the active branch and omits previously sourced answers from the plan input. Ordinary automatic turns also exclude complete history pairs derived from application-plan source or memory grants before planning, counting, summary selection or assembly. The same exclusion checks inherited permission dependencies, so a cached summary cannot reintroduce plan-derived text. Original-key replay of the confirmed plan turn remains available after a later branch turn while its own authority remains current. It uses a local estimated counter and avoids summary generation, automatic memory writes and background inference.

Pending previews reserve capacity before source or memory reads. The fixture retains at most 16 previews or active reservations in total and at most 4 for one authenticated owner and client namespace. A reservation remains held until its worker exits; expiry, failed preparation and cancellation release it. Replacing an offer uses its existing slot until the replacement succeeds.

The native recovery fixture stores immutable per-claim witness records outside the database snapshot. Each record binds the witness epoch, owner, root, attempt and payload digest. The plan attempt checks the exact claim together with the fenced database root before release and again at send authority. This is a disposable local witness; it does not establish hosted witness durability or multi-machine recovery.

Both v2 bridge admission checks run in cancellation-draining workers within the authorization deadline. The final authority check remains under the local durable send-start guard. The plan stream also performs source and identity revalidation through worker calls so those reads do not block the event loop. A revocation after the final check can race the transport write. Data already observed by a recipient cannot be recalled.

## Enroll a synthetic app

The third app uses the Reading contribution's typed projection, record schema, client binding and workspace authority in the shared fixture. The same fixture helper configures a distinct local registration, session and protected storage directory for each owner and app. It then installs exact source and memory grants. The integration test adds Reading to the contribution tuple, seeds its book projection and calls the same onboarding path as Travel and Fitness. This requires changes only to contribution configuration and fixture data.
