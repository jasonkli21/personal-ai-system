1. **Architectural model.** The Application Integration Contract declares typed, versioned operation support; installed domain adapters supply implementation and authority; application policy narrows eligibility. One generic controller manages proposals, exact confirmation and recovery. Model output is candidate provenance only. See [architecture](phase-31-architecture.md) and [adapter contract](../../backend/src/personal_ai/mutations/README.md).
2. **Canonical owners/stores.** Postgres migration `025_mutation_proposals.sql` owns proposal heads and transactional immutable revision audit as one aggregate. External domains own authoritative records, membership, atomic business writes, operation deduplication and post-state. Runtime leases and browser views are never external commit proof. Scoped owner export includes both metadata families; fenced purge cascades audit and does not undo external state.
3. **Identities/versions/epochs.** Distinct owner/verified actor, target app/workspace/entity, client intent key, proposal UUID/revision, operation ID/version/schema, claimed producer/model/endpoint/output reference, source snapshots, shared permission versions/epochs, expected domain revision, domain validation ID/version/exact intent digest, confirmation UUID/exact binding, physical execution UUID, permanent domain-operation UUID, reconciliation UUID and authoritative post-state reference/revision. Provider labels cannot assert verified identity or grant authority.
4. **Generic seams.** Extended application declarations/sidecar policy and the existing installed contribution catalog with independently registered `mutation_adapters`. Strict payload models forbid extras and preserve canonical values. Adapter authorization, validation, execution and reconciliation use no operation-name branches in generic code. Typed public presentation is separate from canonical records; no new grant graph, routing engine or domain database access was introduced.
5. **Production composition.** Installed contribution entry points → `configured_context_runtime`/FastAPI lifespan → canonical application registry and permission revalidators → recent-auth mutation API → persistence factory's `PostgresMutationRepository` → `MutationService` → registered domain adapter. Synthetic integration covers both startup registration and the real API dependency path with an offline store. The shared sidecar accepts an opaque proposal ID and uses the authenticated Next.js proxy; arbitrary assistant/import text has no Apply action.
6. **State/idempotency/reconciliation.** Proposed → validated → confirmed → executing → applied/rejected/uncertain. Invalid validation rejects; pending expiry is terminal. Uncertain → reconciling → applied/rejected/uncertain. Repositories enforce transitions, immutable intent/receipts and CAS. There is at most one physical execution call per proposal. Reservations have a 60-second lease. Timeout, malformed/mismatched receipt, missing receipt and crash after send require observation under the original operation key; no blind resend. Reconciliation can repeat with separate reservations and no automatic retries. Terminal records/keys remain retained until owner deletion; domain deduplication/reconciliation must cover that lifetime. Old operation versions must stay installed while keys remain outstanding.
7. **Authorization/privacy/revocation.** Verified actor must match scope; SQL reads bind owner, actor, app and workspace. Domain authority runs before validation/confirmation/effect and controls post-state reads. Shared dependencies/freshness are checked at pending reads, validation, confirmation and pre-effect; the adapter must atomically recheck authorization/epochs, confirmation/expiry and exact domain revision with its authoritative write. Every candidate is conservatively restricted. Sidecar availability combines support, implementation, policy and current execute authorization. Public views omit dependency tokens. Outcome/status views suppress source-derived patch/rationale/refs/preview while returning a currently domain-authorized post-state reference, including after the write changes its own input revision. Write-policy revocation cannot authorize another send or prohibit authorized reconciliation. No automatic chat/memory/evidence/artifact propagation was added.
8. **Foundational changes and rationale.** Added the planned Postgres proposal authority rather than expanding itinerary generation into a generic writer. Extended the existing application contribution seam instead of a second registry/DI switchboard. Moved the existing CAS conflict exception into the neutral storage boundary; the Postgres import remains an identical-class compatibility re-export. Existing providers, narrow proposal/extraction flows, routing, accounting and grants retain their contracts.
9. **Alternatives considered.** Rejected Apply-on-text, provider provenance as permission, generic domain writes, process-local execution flags, new attempt keys after timeout, cached/versionless confirmation, duplicate policy/grant graphs and domain-name orchestration switches. Rejecting undeclared live operations preserves authority until domain-owned contracts exist.
10. **Downstream impact.** Phase 36 consumes synthetic mutation conformance, isolation, restart and deletion evidence. Future domain adapters extend registration and must prove their own atomic authorization/version/deduplication semantics. Phases 32–34 retain their source-truth/permission boundaries; Phase 35 retains inference observations rather than treating mutation receipts as provider outcomes. Existing Phase 15/21 routing and domain identity gates are unchanged.
11. **Open external/integration verification.** Migration 025 and real target-store CAS/export/fence behavior remain externally unverified. Tests are maintained in `tests/persistence/test_mutations.py`. Actual domain atomic transactions, durable receipts/idempotency lifetime, delegated identity, deployed workspace membership, cloud IAM and browser host integration still need accepted domain adapters/environments. No synthetic result claims those properties are production-proven. Root README was updated for the framework and unavailable live writes.
12. **Independent reviewer challenge areas.** Challenge exact validation/confirmation digest coverage; source-authority proofs and domain check/write races; delegate identity and SQL scope isolation; delayed execution versus reconciliation; original-key receipt retention/removal; stale-source versus authorized post-state disclosure; audit/export/deletion and restore boundaries; immutable operation versions; payload size/sensitivity; production catalog wiring and unsupported implementation denial. Future code must consume the public projection or revalidate source dependencies before using canonical proposal payloads. Rewrite risk is high for this contract, so domain authority and one canonical metadata owner are explicit.
