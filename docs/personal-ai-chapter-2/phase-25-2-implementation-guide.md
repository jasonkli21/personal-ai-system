# Phase 25.2 implementation guide

This phase implements an internal, gated external-turn state machine. See the [architecture and rewrite-risk review](phase-25-2-architecture.md) and [verification evidence](phase-25-2-implementation-evidence.md). HTTP/context-selector/manual-import UI remains Phase 25.3 work.

`contracts.execution.ExecutionChoice` selects automatic, connected-provider, or manual-external execution. `ContinuationRequest` adds content, an idempotency UUID, and optional active completed-turn narrowing. Ordinary continuation enters `ChatTurnService.continue_turn`; external choices enter `ExternalTurnService.prepare`, which delegates to the same chat preparation machinery. Provider choice never authorizes disclosure.

Compose external preparation with the same conversation/message repositories, resolved authenticated application context, planner, registered context providers and permission revalidator. Use `EstimatedTokenCounter`, no summary generator, and a required `ExternalTurnAuthority` integration. Its current snapshot must reject unverified membership/caller/account bindings, changed or missing source/grant dependencies, and stale fetched-source versions. Default app policies allow no external modes. No permissive implementation is included. Do not mount the service while P14/P15 and bridge live gates remain open.

Register exact P18 endpoint profiles and access/data-use policy. ChatGPT-plan requires public-client OAuth, explicit selection, user-local credentials, account-specific discovery, subscription cost, automation exclusion and no hosted history. Do not register it as a P19 strict-free bucket or route it through automatic evaluation/fallback. Explicit endpoints are refreshed and revalidated by exact profile version/body, never provider/model name alone.

A prepared result contains transient exact messages, an estimated count label, the canonical reservation, and either a connected version-2 package or a portable manual prompt. Connected dispatch requires a server-only `DispatchGrantSigner` with a pinned public verifier at the bridge. The service signs only after policy/profile rechecks and returns the proof only after branch/message CAS. Keep signing-key custody outside source code and out of browser/bridge credentials. The bridge still owns its authenticated physical-send fence and local compatibility/model gates.

Call `finalize` with a neutral `ExternalCompletion` and matching reservation fingerprint. Manual finalization also requires explicit import. Declarations are bound at preparation and remain optional/unverified. Connected completion metadata must match the reserved producer and connection; it is client-reported, not server billing/model evidence. `report_failure` accepts only bounded normalized recovery codes and leaves issued dispatches uncertain. `abandon` and stale recovery retain terminal fences with empty text. Manual imports create no latency, usage, account, reset, quota, or billing facts.

Identical completed imports/completions replay without another send or write. Changed replay inputs fail. Repeated preparation cannot recover transient prompt bodies or reissue dispatch proofs; use the canonical reservation's get/finalize/cancel paths or a new explicitly requested preparation. The service remains synchronous at this internal boundary; future routes must use the existing async IO boundary rather than blocking the event loop.

Safe local connection projections add coarse usage observations and recovery hooks (`local_operator`, `local_operator_new_pairing`, `provider_account_ui`). No URLs/auth secrets/reset guesses are copied to managed metadata. Account/scope/model changes require fresh preparation; connection revisions invalidate local pairing, and prior completed producer attribution stays immutable.

Repository tests cover offline policy/provenance/lifecycle/replay/continuation behavior. `tests/persistence/test_external_turns.py` supplies opt-in DynamoDB race/restart/expiry checks using `PERSISTENCE_TEST_DYNAMODB_ENDPOINT`. Run the established Makefile commands; synthetic results do not establish target-store, provider, browser, cloud or account acceptance.
