# Phase 31 authoritative external-effect contract

Design established on 2026-10-11 before implementation. This extends the Application Integration Contract and installed application contributions, rather than making the existing itinerary-generation controller a write controller.

Personal AI owns immutable proposal intent and its validation/confirmation/execution/reconciliation metadata in Postgres. Domain applications alone own membership, business authorization, exact entity versions, authoritative writes, operation deduplication and post-state. Application declarations own operation ID/version/schema/entity-kind/sensitivity metadata. Installed adapters independently supply implementations. Application sidecar policy can only narrow declared operations; all current domain applications declare no safe writes and therefore remain unavailable.

Identity families are distinct: owner and authenticated acting user; request app/workspace and target entity; proposal/client intent key; typed operation ID/version/payload schema; source snapshots and permission revisions; claimed producing provider/model/endpoint provenance; expected domain revision; domain validation ID/version/dependencies/preview/expiry; exact confirmation ID/digest; single physical execution attempt ID; permanent domain-operation key; reconciliation attempt ID; authoritative post-state reference and revision. Provider provenance grants no authority. Changed intent needs a new proposal and confirmation.

State transitions: proposed → validated/rejected/expired; validated → confirmed/rejected/expired; confirmed → executing/rejected/expired; executing → applied/rejected/uncertain; uncertain → reconciling; reconciling → applied/rejected/uncertain. Applied, rejected and expired are terminal. Postgres CAS claims the execution before invoking transport. There is at most one execution call per proposal. A crash in executing or reconciling leaves a durable reservation. After its lease ends, recovery only queries the domain under the original operation key; it never sends another mutation. Unknown/absent domain results remain uncertain, including after expiry. Successful transport alone is insufficient: an exact domain receipt with authoritative post-state is required.

Before sensitive reads, validation, confirmation and effect, shared source/permission dependencies and expiry are checked and domain authorization is consulted using authenticated delegated identity. The domain execution adapter must atomically authorize current identity/permission revisions, compare the exact entity revision and deduplicate the operation key with its write. Generic preflight cannot close that transaction race. Reconciliation authorizes current reads but does not require old source grants to remain valid: it observes an already possible effect without redisclosing revoked proposal data. Revoked dependencies prevent payload/preview reuse and pending sensitive API reads. Outcome/status presentations omit all input payload/rationale/source refs/preview; current domain read authority independently controls authoritative post-state references, so an operation changing its own input revision does not suppress the authorized receipt. Write-policy narrowing does not prevent observation-only reconciliation. Old declared versions/adapters must remain installed while their keys are outstanding. No proposal is automatically copied into chat, memory, artifacts or evidence. Derived future consumers must carry the existing shared dependencies.

Postgres heads and immutable revisions are one aggregate store, not independent authority. Revision writes and audit append share a transaction; owner deletion fences block reads/writes and purge cascades audit revisions. Scoped account export includes both families. Records and operation tombstones are retained until fenced owner deletion; domain operation deduplication must survive at least that lifetime and domain reconciliation must remain available after request expiry. Deleting AI metadata neither rolls back nor deletes authoritative domain records; independent domain account lifecycle remains authoritative. Bulk document/output storage is not introduced; bounded control payloads are rejected above limits. Migrations contain only immutable SQL.

The production path is installed contribution catalog → shared runtime mutation-adapter map → authenticated API dependency + application declarations/policy + shared permission registry + Postgres repository → mutation controller → domain adapter. The shared sidecar retrieves a proposal by opaque ID, reviews domain preview, confirms its exact digest, applies or reconciles, and displays authoritative post-state references. Arbitrary assistant text has no Apply action. Synthetic operations use this same composition, without app/operation branches in control flow.

Routing/accounting are unchanged: this phase creates no inference turn. Existing model outputs may be converted by a domain integration into typed proposal candidates; any future conversion inference must use the shared assembler/routing/accounting path. Phase 36 consumes this contract for synthetic application conformance and interrupted-effect tests; Phase 35 retains its existing inference observation contracts; mutation receipts must not become provider quality or accounting evidence. Phases 32–34 must not promote proposals or provider output to source truth.
