# Phase 30 authorization and provenance model

Design baseline: 2026-10-11. Domain truth remains in each application's registered read adapter. The shared context coordinator owns preparation, projection, budgets and disclosure. Federation is an optional registered context provider, not a second orchestrator. Source export declarations advertise capability; deployment allowlists and executable adapters are separate from permission.

Postgres owns owner-wide grant heads and append-only grant revisions. Authenticated owner identity authorizes grant mutation; acting user identity is separately bound to the grant and supplied by authentication, never client context. Source/destination application and workspace, exact category/fields/entities, purpose, expiry, server-owned issuance UUID, revision, epoch, revocation ID, source-policy dependency and sensitivity ceiling are explicit. Empty entity/field scope is forbidden. Delegation/re-delegation is denied. A revoked grant is terminal; a new authorization requires a new grant ID. Each creation lifetime has a server-owned issuance UUID that selections, revoke requests and shared dependency versions bind; even physical deletion and creation-key reuse cannot revive old references. Updates use revision CAS and advance the epoch; historical revisions cannot authorize reads. Expiry denies without needing a scheduled transition. Owner deletion fences creation and updates.

A broker validates destination policy, the current grant, current source-policy dependencies and the registered adapter’s exact category/field/entity/purpose export eligibility before source retrieval; it reloads the current grant after the bounded source eligibility check and repeats authorization after retrieval and the shared dependency revalidator checks later prepare/disclosure/finalization/reuse boundaries. Source adapters own membership, export eligibility and exact source revision dependencies. Narrow exports must be supplied by adapters rather than projected after fetching a broad source record. No destination domain database access is permitted. Unknown source policy, identity, adapter, category, revision, freshness or sensitivity fails closed. The most restrictive source/field/grant classification survives; destination policy can only narrow admission.

Destination-owned context envelopes retain separate source app/workspace/entity references, exact source revisions and fingerprints, grant dependencies and source dependencies. These envelopes are disclosure provenance, not copies of grant authority or domain truth. Source adapters register through `ContextRuntimeContribution.export_adapters`; deployment allowlisting installs broker providers and reconciles their existing typed capability metadata. The grant authority retains the same registered provider references as a derived lookup index, not another grant/policy store, and runs their export eligibility checks during later reuse. Existing permission dependencies flow through history/summary snapshots, memory checks, caches and artifacts; unknown dependencies fail closed. Federated assistant output is ineligible for automatic durable memory extraction. External/manual context uses this same provider and grant, with the additional existing sidecar sensitivity/disclosure policy. Labels identify source category explicitly without exposing entity IDs.

Reads have no external mutation/send idempotency state. Grant writes are transactional CAS; API creation keys derive owner-bound IDs, identical create/revoke retries return canonical state, changed intent and stale updates conflict, and revocation is terminal. Concurrent revocation after a source read prevents returning its payload; later revocation is checked again at reuse/disclosure boundaries. No cross-store transaction is claimed. Selection digests and safe authorization/exclusion codes use the existing relational audit-event store. Postgres owner export includes heads/revisions; existing derived records retain dependencies in their own export/deletion inventory. Grant deletion cannot make a dangling dependency valid. Physical owner cleanup remains subject to the repository's existing incomplete account cleanup acceptance.

Initial deployment declarations are Health dietary restrictions to Travel, Health ergonomic constraints to Shopping, Travel trip to Shopping and Finance discretionary budget to Shopping. They stay unavailable until independently authenticated, narrow domain export adapters exist; broad current read contracts and Health's unavailable delegated identity are insufficient. A synthetic adapter can use precisely the same runtime registration path without expanding this production allowlist. Phases 31, 32 and 36 should extend these permission dependencies and export adapters, not invent a new federation graph.
